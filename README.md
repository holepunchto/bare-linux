# bare-linux

An example Linux app that embeds the Bare runtime via bare-kit to run the same peer-to-peer shared switch as `bare-macos`, with a native host written in C. The JavaScript half (Hyperswarm worklet, switch logic, schema) is the shared `bare-switch-core` package; the native half is rewritten in C against bare-kit's C API and the typed RPC client generated by `hrpc-c`.

### Status as of 2026-06-23: Phase 0 is complete

The native boundary works end to end on Linux (built and run on arm64; CI also covers x64):

- **Repo scaffold + tooling** (`package.json`, standard dotfiles) - bare-switch-core as the one JS dependency.
- **Prebuilt `libbare-kit.so`** fetched from the bare-kit release (v2.3.0), plus `bare-headers` for the real `uv.h`.
- **Echo IPC round-trip** - a throwaway worklet proved worklet boot and bidirectional bytes over the bare-kit IPC channel (kept only in git history; `main.c` is now the real host).
- **The real Hyperswarm backend, headless** - the host boots `bare-switch-core`'s `backend.js`, owns a real Hyperswarm node, and drains the IPC channel. Two instances discover each other on the DHT and exchange `peersChanged` / state frames - the headless equivalent of launching two copies of the macOS app.
- **CI** - lint plus a build-and-boot smoke test on both `ubuntu-latest` (x64) and `ubuntu-24.04-arm` (arm64).

**Realignment from the plan:** the JS half is no longer vendored. bare-macos was refactored to depend on the published `bare-switch-core` package and pack its `backend.js`; bare-linux now does the same. Phase 1 C codegen will run against that package's committed `spec/` JSON, mirroring bare-macos's `project.yml`.

## Building and running

The build needs Linux. On an Apple Silicon Mac, run everything inside a Linux arm64 VM (a Lima Ubuntu instance with this repo mounted; `npm install` and the toolchain go inside the VM, since `node_modules` holds platform-specific native binaries). The toolchain is `build-essential` + `cmake` + `clang` (bare-make drives Clang/Ninja) + Node.

From the repo root (each step auto-detects the host arch):

```sh
npm install
npm run fetch    # download the prebuilt libbare-kit.so for this arch
npm run bundle   # link the native addons + pack the worklet
npm run build    # generate + build the C host
npm start        # run it - launch twice to watch peers find each other on the DHT
```

To verify a build non-interactively, `npm run smoke` boots the host, confirms an IPC frame arrives, and exits non-zero if none does - this is exactly what CI runs.

`npm start` sets `LD_LIBRARY_PATH=app/addons/lib` because the linked native addons (`sodium-native`, `udx-native`, ...) are `dlopen`ed by the runtime from inside `libbare-kit.so`, so the executable's rpath does not cover them. The worklet's own `console.log` does not surface on the host's stdout in this bare-kit build, so the `[host] ipc frame: N bytes` lines are the signal that the channel is live.

## What's next: Phase 1 (typed RPC)

Phase 1 was gated on three upstream pieces that have all since landed: librpc's fixed-width-type fix, `hrpc-c`'s unary + event codegen, and librpc's `rpc_client_t` runtime. `hrpc-c`'s `test/e2e.test.js` proves the generated encode -> dispatch -> reply -> `rpc_client_read` -> decode path composes, so the layers this app builds on are known to work. The switch demo uses only unary (`set-state`) and send-only events (`new-state`, `peers-changed`, `info`), so it never needs the streaming codegen.

## Key integration facts for Phase 1

These are the concrete details a fresh session needs; they were settled while building the upstream stack.

**The transport is the bare-kit IPC channel, not a socket.** This is why no libuv adapter is needed (the SPEC's optional `rpc_client_t` uv adapter was deliberately deferred). bare-kit already gives you a readiness callback via `bare_ipc_poll`. Wire `rpc_client_t` to it directly:

- On readable (`bare_ipc_poll_start(..., bare_ipc_readable, cb)`): `bare_ipc_read(ipc, &data, &len)` then `rpc_client_read(client, data, len)`. `rpc_client_read` accepts arbitrary byte chunks and reassembles frames internally - feed it whatever IPC hands you.
- To send a request/reply: call the generated `<ns>_encode_*` to get a heap buffer, `bare_ipc_write(ipc, buf, len)`, then `free(buf)`.
- The poll callback runs on bare-kit's IPC thread, its own pthread on Linux (Phase 2 note: marshal to the GTK main thread with `g_idle_add` before touching widgets).

**`rpc_client_t` API** (`#include <rpc/client.h>`, from librpc `main`):

- `rpc_client_init(rpc_client_t *c, rpc_client_cb on_message, void *data)` - `on_message` is the fallthrough for events/streams; `data` is its context.
- `uint64_t rpc_client_next_id(c)` - monotonic from 1, for each request.
- `rpc_client_track(c, id, cb, data)` - register a one-shot callback for a request's reply.
- `rpc_client_untrack(c, id)` - cancel a pending request (timeouts/teardown).
- `rpc_client_read(c, buf, len)` - feed inbound bytes; resolves a tracked reply (a `rpc_response` with `stream == 0`, matching the id) via its callback, routes everything else (events, streams) to the fallthrough. Returns `< 0` on error (`rpc_client_err_alloc`/`_decode`/`_reentrant`).
- `rpc_client_destroy(c)` - frees state; invokes no callbacks.
- Reentrancy + memory: do NOT call `rpc_client_read` from within a callback. The `rpc_message_t` a callback receives has views into the runtime's buffer, valid only during the callback - copy out (decode) anything kept.
- Correlation is the consumer's job: store id->command when you call `next_id`, look it up in the callback to pick the right generated `*_decode_*`.

**Generated code** (from `hyperschema-c` + `hrpc-c`): bare-switch-core already commits the JS + Swift outputs under its `spec/`; Phase 1 adds a C emit. For namespace `sync`, expect `sync_encode_set_state(id, args, **out, *len)`, `sync_decode_set_state_response(msg, *result, *error)` (error arm: a `rpc_response` with `error == true`), `sync_<target>_dispatch(...)` for the server side, and `sync_encode_<event>` / `typedef void (*sync_on_<event>)(ctx, req)` for the send-only events. Confirm exact names by reading the generated `sync_hrpc.h` after Task 1.1.

**Build (Phase 1 additions):** add `cmake-bare` + `cmake-fetch` back to the top-level CMake and `fetch_package` `librpc` + `libcompact`; build the generated C against them. (Phase 0's host links only the prebuilt `libbare-kit.so`.)
