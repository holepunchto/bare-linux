# bare-linux

An example Linux app that embeds the Bare runtime via bare-kit to run the same peer-to-peer shared switch as `bare-macos`, with a native host written in C. The JavaScript half (Hyperswarm worklet, switch logic, schema) is copied verbatim from `bare-macos`; the native half is rewritten in C against bare-kit's C API and the typed RPC client generated by `hrpc-c`.

## Key integration facts for Phase 1

These are the concrete details a fresh session needs; they were settled while building the upstream stack.

**The transport is the bare-kit IPC channel, not a socket.** This is why no libuv adapter is needed (the SPEC's optional `rpc_client_t` uv adapter was deliberately deferred). bare-kit already gives you a readiness callback via `bare_ipc_poll`. Wire `rpc_client_t` to it directly:

- On readable (`bare_ipc_poll_start(..., bare_ipc_readable, cb)`): `bare_ipc_read(ipc, &data, &len)` then `rpc_client_read(client, data, len)`. `rpc_client_read` accepts arbitrary byte chunks and reassembles frames internally - feed it whatever IPC hands you.
- To send a request/reply: call the generated `<ns>_encode_*` to get a heap buffer, `bare_ipc_write(ipc, buf, len)`, then `free(buf)`.
- The poll callback runs on bare-kit's IPC thread (Phase 2 note: marshal to the GTK main thread with `g_idle_add` before touching widgets).

**`rpc_client_t` API** (`#include <rpc/client.h>`, from librpc `main`):

- `rpc_client_init(rpc_client_t *c, rpc_client_cb on_message, void *data)` - `on_message` is the fallthrough for events/streams; `data` is its context.
- `uint64_t rpc_client_next_id(c)` - monotonic from 1, for each request.
- `rpc_client_track(c, id, cb, data)` - register a one-shot callback for a request's reply.
- `rpc_client_untrack(c, id)` - cancel a pending request (timeouts/teardown).
- `rpc_client_read(c, buf, len)` - feed inbound bytes; resolves a tracked reply (a `rpc_response` with `stream == 0`, matching the id) via its callback, routes everything else (events, streams) to the fallthrough. Returns `< 0` on error (`rpc_client_err_alloc`/`_decode`/`_reentrant`).
- `rpc_client_destroy(c)` - frees state; invokes no callbacks.
- Reentrancy + memory: do NOT call `rpc_client_read` from within a callback. The `rpc_message_t` a callback receives has views into the runtime's buffer, valid only during the callback - copy out (decode) anything kept.
- Correlation is the consumer's job: store id->command when you call `next_id`, look it up in the callback to pick the right generated `*_decode_*`.

**Generated code** (from `hyperschema-c` + `hrpc-c`, committed under `spec/`): for namespace `sync`, expect `sync_encode_set_state(id, args, **out, *len)`, `sync_decode_set_state_response(msg, *result, *error)` (error arm: a `rpc_response` with `error == true`), `sync_<target>_dispatch(...)` for the server side, and `sync_encode_<event>` / `typedef void (*sync_on_<event>)(ctx, req)` for the send-only events. Confirm exact names by reading the generated `spec/sync_hrpc.h` after Task 1.1.

**Wiring reference:** `hrpc-c`'s `test/e2e.test.js` is a worked example of the full client side - `next_id` -> encode -> `track` -> feed reply bytes to `rpc_client_read` -> decode in the callback; and a response-stream via the fallthrough. The bare-linux host does the same, with `bare_ipc_*` as the byte transport instead of an in-process loopback.

**Build:** `bare-make` + `cmake-bare` + `cmake-fetch`; pack the worklet with `bare-pack --preset linux`, link addons with `bare-link --preset linux`. `fetch_package` `librpc` + `libcompact` in the generated `spec/` CMake. Fetch the prebuilt `libbare-kit.so` from the bare-kit release (Phase 0 Task 0.1).
